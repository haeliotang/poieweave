# Release Signing 与信任锚设计（未实现）

日期：2026-11-15
状态：设计说明；当前只有临时密钥的签名 plating 测试，**没有发布信任锚**

## 1. 现状

- `certificate-attestation` 每次运行生成临时 RSA 密钥，签名 bundle digest，并验证篡改失败。
- 它证明签名/验证管线可用，但**不能**证明发布者身份，也不能作为第三方信任依据。
- 没有持久私钥、密钥托管、轮换、撤销或透明日志。

## 2. 目标

让第三方能够回答：

1. 这个 bundle 是否由 Poieweave 发布者签署？
2. 签名后 bundle 是否被修改？
3. 签署时使用的是哪个密钥/身份？
4. 若密钥泄露，如何撤销和重签？

## 3. 可选信任锚

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 离线发布密钥 | 简单、可审计 | 托管与轮换成本高 |
| CI OIDC 短期证书 | 无长期私钥 | 依赖 CI 身份与日志 |
| 透明度日志 | 可检测回滚/替换 | 需要外部基础设施 |

当前不选择具体方案；先记录比较，避免把临时自签测试误当成发布签名。

## 4. 发布证据应包含

- bundle SHA-256
- 签名与证书链/身份
- 签名时间与有效期
- 密钥 ID、轮换代次
- 发布版本与 commit
- 撤销/重签记录（若有）
- 验证命令与预期输出

## 5. 密钥治理最低要求

- 私钥不进入仓库、CI 日志或构建产物
- 至少双人审批发布
- 密钥轮换与撤销流程有文档
- 签名失败不得静默降级
- 旧版本 bundle 的验证路径保持可用

## 6. 当前结论

发布签名与信任锚**未实现**。在完成密钥托管、身份绑定、轮换/撤销与第三方验证之前，Poieweave 的 bundle 只能作为内容寻址证据，不能作为可信发布声明。
